# ADR 0005: Creator Authentication (Supabase Auth JWT)

## Status
Accepted

## Context
Creators must authenticate to the API to create their channel and manage its
PIN. Supabase Auth already manages creator accounts (email/password, magic
link) and issues access tokens to the frontend, so we need a way for the
backend to verify those tokens and map them to the `creators` table.

Constraints that shaped the decision:
- ADR 0002 gives RLS policies of the form `creator_id = auth.uid()`, i.e. the
  Supabase user id is the intended creator identity.
- The backend's DB connection is **privileged** (service-role credentials; RLS
  is bypassed on the application path), so RLS alone cannot enforce ownership
  for API requests.
- The API must never expose `channels.pin_hash` or `channels.signing_key`.

## Decision
**Verify Supabase Auth access tokens in the backend and use the `sub` claim as
the creator id.**

1. **Token format**: Supabase signs access tokens with the project JWT secret
   (HMAC). The backend verifies them with `pyjwt`:
   `jwt.decode(token, settings.supabase_jwt_secret, algorithms=["HS256"],
   audience="authenticated")`.
2. **Identity**: `creators.id == auth.uid() == token.sub`. The `sub` claim (a
   UUID) is the primary key of the `creators` row — it is never generated by
   the API, it comes from the verified token (see
   `CreatorRepo.upsert`).
3. **Configuration**: `SUPABASE_JWT_SECRET` is a required setting. If it is
   empty the auth dependency fails loud with **500 "auth not configured"** —
   an unconfigured server must never silently accept tokens.
4. **Failure modes**: missing/malformed `Authorization: Bearer <token>`,
   signature mismatch, expiry, wrong audience, or a non-UUID `sub` all return
   **401**.
5. **Ownership enforcement**: because the application DB connection bypasses
   RLS, every endpoint that mutates a creator-owned row checks
   `channel.creator_id == auth.uid()` **in the API layer** (403 otherwise).
   RLS (ADR 0002) stays enabled as defense-in-depth for direct/analyst access
   and future SECURITY DEFINER paths.
6. **Claims used**: the `email` claim populates `creators.email`; tokens
   without an `email` claim fall back to `f"{sub}@placeholder.local"` (the
   column is NOT NULL, and the placeholder is deterministic per user).

Implemented in `backend/app/core/auth.py`
(`get_current_creator_id` / `get_current_creator`), consumed by
`backend/app/api/channels.py`.

## Consequences
- **Pros**:
  - No custom session/JWT machinery: Supabase remains the single source of
    creator identity, and `auth.uid()` in RLS policies and API ownership
    checks refer to the same id.
  - HS256 verification is stateless and cheap (one HMAC per request).
  - Fail-loud misconfiguration (500) prevents a token-less auth bypass.
- **Cons / risks**:
  - The backend holds the same symmetric secret Supabase signs with: any
    process that can read `SUPABASE_JWT_SECRET` can mint creator tokens.
    Mitigation: secret lives only in server env, never in the repo or logs.
  - One channel per creator and handle uniqueness are enforced only by the
    API layer today: `channels.creator_id` has **no** UNIQUE constraint yet
    (handle uniqueness is DB-backed). Adding `UNIQUE (creator_id)` is a
    pending schema fix tracked in the pivot plan.
- **Follow-ups**:
  - **UNIQUE (creator_id) on channels**: closes a race where two concurrent
    requests could create two channels for one creator.
  - **Asymmetric JWTs (RS256/JWKS)**: migrate verification to Supabase's JWKS
    endpoint so the backend only holds public keys and cannot forge tokens.
  - **Frontend identity bridge**: Privy (Apple/Google/email login) mints the
    embedded wallet and bridges into a Supabase session so `sub` stays the
    creator id (ADR 0006); verify against Privy docs before frontend tasks.
  - **Webhook `signing_key` delivery**: the channel's signing key is generated
    at channel creation but deliberately not returned by the API; how the
    creator retrieves it (dashboard + webhook verification) is a separate
    task.
